# ADR 0002. Смена состояния синхронно, проверка SLA в фоне

- Дата: 2026-11-15
- Статус: принято

## Контекст и ограничения

Создание инцидента, назначение и смена состояния должен увидеть тот же HTTP-запрос. Проверка десятков открытых инцидентов по таймеру в этот запрос не входит. Уведомление ходит во внешний сервис и может молчать. Заявка требует, чтобы недоступность уведомлений не отменяла уже сохранённую эскалацию. Повтор одного и того же запроса не должен создавать второй Job.

## Решение

`POST /jobs`, назначение, `transition` и `change_priority` выполняются синхронно. Новое состояние и строка истории фиксируются в одной транзакции до ответа клиенту. Планировщик в том же процессе периодически ищет просроченные сроки и вызывает `EscalationTool`. Эскалация сохраняется до вызова адаптера. Повтор той же причины для того же Job возвращает уже записанную эскалацию со статусом `200` и не создаёт второе уведомление. После перезапуска процесса состояние читается из PostgreSQL. Незафиксированная транзакция пропадает, зафиксированная остаётся. Следующий тик планировщика продолжает проверку.

Ключ `Idempotency-Key` хранится вместе с телом первого `POST /jobs`. То же тело возвращает прежний Job. Другое тело с тем же ключом получает `409 idempotency_conflict`. Тот же `source_event_id` возвращает прежний Job даже при новом ключе.

## Рассмотренные альтернативы

1. Вся обработка, включая уведомление и проверку всех сроков, внутри запроса клиента. Отвергнуто: клиент ждёт внешний сервис, а обрыв ответа после сохранения оставляет его без понятного повтора.
2. Очередь сообщений между API и планировщиком. Отвергнуто для первой версии: брокер не требуется скелетом проекта и добавляет второй механизм доставки.

## Цена решения

Окно между коммитом эскалации и ответом внешнего сервиса есть всегда. Клиент может увидеть `ESCALATED` раньше, чем руководитель получит уведомление. Повторная доставка уведомления лежит на адаптере, а не на смене состояния. Планировщик обязан быть один логически: два перекрывающихся тика опираются на уникальность пары Job и причины.

## Условия пересмотра

Решение пересматривается, если уведомление должно быть строго в той же транзакции, что и состояние, либо если запускается больше одного экземпляра API и тики планировщика перестают сериализоваться одной записью в базе.
