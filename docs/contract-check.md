# Проверка контракта колодой

Карты К1–К10 сверялись с `docs/api/openapi.yaml`, `docs/job-states.md`, `docs/tool-contract.md` и ADR.

| Карта | Ответ контракта |
|---|---|
| К1 Двойной клик | Один Job. Второй `POST /jobs` с тем же `Idempotency-Key` и тем же телом — `200` и прежний `id`. `openapi.yaml`, ответ `200` у `POST /jobs`. |
| К2 Ответ потерялся | Клиент повторяет тот же `POST /jobs` с тем же ключом и телом и получает прежний Job. Текущее состояние читается `GET /jobs/{id}`. |
| К3 Неизвестная операция | `POST /jobs/{id}/operations` с именем вне `assign`, `transition`, `change_priority`, `escalate` — `400 unknown_operation`. Job не создаётся и не меняется. |
| К4 Кривые параметры | Нет поля, неверный тип или недопустимое значение — `400` или `422 invalid_params`, в `details.field` имя поля. Для решения без текста поле `resolution`. |
| К5 Воскрешение | Из `CLOSED` и `CANCELLED` любой переход — `409 invalid_transition`, см. `job-states.md`. Из `RESOLVED` назад только в `IN_PROGRESS`, прежний текст решения остаётся в истории. Новый запуск — новый `POST /jobs`. |
| К6 Отмена | В `CANCELLED` можно перейти из `OPEN`, `IN_PROGRESS` и `ESCALATED`. История сохраняется. Из `RESOLVED` отмена — `409`. |
| К7 Огромный вход | Тело больше 64 КБ или `description` длиннее 10 000 символов — `413 payload_too_large` до создания Job. |
| К8 Чужой или несуществующий id | `404 job_not_found` без лишних полей. Отдельного чужого клиента в первой версии нет: одна организация, это записано в ADR 0001. |
| К9 Перезапуск сервера | Состояние после старта берётся из PostgreSQL. Незакоммиченная смена пропадает, закоммиченная остаётся. Следующий тик планировщика продолжает SLA. Повтор той же причины возвращает `200` и вторую эскалацию не создаёт. ADR 0002 и `EscalationTool`. |
| К10 Внешний сервис | Молчание, мусор или переименованное поле: Job остаётся `ESCALATED`, адаптер делает ограниченный retry, в истории ошибка доставки. Отката эскалации нет. `tool-contract.md`, адаптер уведомлений, ADR 0002. |

## Что предложил ИИ

Промпт:

> Ты атакующий. Контракт Oscar SLA Monitoring: POST /jobs требует Idempotency-Key; то же тело возвращает прежний Job, другое тело с тем же ключом даёт 409. GET /jobs/{id} для неизвестного id даёт 404. POST /jobs/{id}/operations принимает assign, transition, change_priority, escalate. Ошибка всегда error.code, error.message, error.details. Состояния: OPEN, IN_PROGRESS, ESCALATED, RESOLVED, CLOSED, CANCELLED. Найди три ситуации вне карт К1–К10, на которые контракт может не ответить. Для каждой дай конкретный запрос.

1. Два тика планировщика одновременно видят одну просрочку одного инцидента. Принято. `EscalationTool` хранит одну эскалацию на пару Job и `reason`, повтор возвращает прежнюю запись со статусом `200` и не шлёт второе уведомление. Это записано в контракте Tool и в ADR 0002.
2. Мониторинг повторяет событие без прежнего `Idempotency-Key`, но с тем же `source_event_id`. Принято. Повтор такого id в `POST /jobs` возвращает `200` и уже созданный Job. Поле есть в `CreateJob`.
3. `change_priority` приходит в ту же секунду, когда планировщик прочитал старый срок. Принято. Смена приоритета и новые сроки пишутся одной записью. Повтор эскалации той же причины возвращает `200` и второй раз не ставится. Операция `change_priority` есть в OpenAPI, атомарность — в ADR 0002.
