# CONTRIBUTING

## Общий процесс

Разработка ведётся через Issues, отдельные ветки и Pull Requests. Рабочая ветка по умолчанию — `main`; прямые изменения в неё не вносятся, кроме первоначального bootstrap-коммита пустого репозитория.

**Одна задача — одна ветка — один Pull Request.**

## Участники и маркировка вклада

Плановые участники команды:
- `seaz96`
- `qwuipss`
- `Serega372`

Формат сообщения:

`<type>: <краткое описание>`

Примеры:
- `docs: describe project scope`
- `docs: add SLA scenarios`
- `docs: add AI analysis`

## Ветки

Формат имени ветки:

`<type>/<participant>-<short-description>`

Допустимые типы:
- `feat/` — новая функциональность;
- `fix/` — исправление ошибки;
- `docs/` — документация;
- `test/` — тесты;
- `refactor/` — рефакторинг;
- `chore/` — инфраструктура и обслуживание.

Примеры:
- `docs/seaz96-project-overview`
- `docs/qwuipss-status-sla`
- `docs/serge-resolution-ai-contributing`

Новая ветка создаётся от актуальной `main`. Название ветки должно быть коротким и отражать задачу.

## Коммиты

Используется упрощённый Conventional Commits:
- `feat` — новая функциональность;
- `fix` — исправление ошибки;
- `docs` — документация;
- `test` — тесты;
- `refactor` — рефакторинг;
- `chore` — технические изменения;
- `ci` — изменения CI.

Коммиты должны быть небольшими и отражать одно логическое изменение.

## Code Review

Содержательное Code Review должно проверять:
- соответствие требованиям и критериям приёмки;
- корректность бизнес-логики и переходов Job;
- обработку негативных сценариев и отказов внешних зависимостей;
- согласованность документации, API и доменной модели;
- отсутствие лишних изменений и секретов.

Замечание должно указывать конкретный фрагмент, проблему и ожидаемое исправление. Автор PR должен ответить на замечания и внести исправления отдельными коммитами до слияния.

## Definition of Done

Задача считается завершённой, если:
- выполнены все требования и критерии приёмки связанной Issue;
- изменения соответствуют архитектуре и границам проекта;
- добавлены или обновлены необходимые тесты;
- тесты и CI проходят успешно, если применимо;
- документация обновлена;
- содержательные замечания review обработаны;
- PR объединён с `main`;
- связанная Issue закрыта.

Для изменений схемы БД обязательны миграции и проверка их применения на чистой базе. Для внешних HTTP-интеграций обязательны timeout, ограниченный retry, обработка недоступности и некорректного ответа, а также fake-сервис для тестирования.

## Инженерные правила проекта

- Доменное ядро не зависит от веб-фреймворка и конкретной СУБД.
- Dispatcher работает через общий контракт Tool и Registry, а не через конкретные классы инструментов.
- Недопустимые переходы Job отклоняются без изменения состояния.
- Внешние сетевые зависимости вызываются через адаптеры.
- API использует единый машиночитаемый формат ошибок.
- Конфигурация загружается из переменных окружения.
- Секреты и токены не хранятся в Git и не попадают в логи.
