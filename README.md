# Oscar SLA Monitoring

**Команда:** oscarcat443  
**Тип проекта:** сервис регистрации и обработки IT-инцидентов с контролем SLA.

## Какую проблему решает сервис

Oscar SLA Monitoring помогает IT-поддержке регистрировать инциденты, назначать ответственных, отслеживать сроки реакции и устранения проблем, а также своевременно эскалировать просроченные обращения. Сервис сохраняет историю обработки, чтобы команда могла восстановить ход работы и понять, где возникла задержка.

## Для кого предназначен

- **Инициатор (Reporter)** — сообщает о проблеме и отслеживает её статус.
- **Диспетчер (Dispatcher)** — распределяет инциденты между исполнителями.
- **Исполнитель (Assignee)** — устраняет проблему и фиксирует результат.
- **Руководитель (Manager)** — контролирует SLA и обрабатывает эскалации.

## Что входит в систему

- регистрация инцидентов с категорией, приоритетом и описанием;
- назначение и переназначение исполнителей;
- управление жизненным циклом инцидента с проверкой допустимых переходов;
- расчёт и контроль сроков реакции и решения по SLA;
- эскалация просроченных инцидентов;
- фиксация решения, подтверждение и закрытие;
- история изменений и действий;
- отправка уведомлений через внешний HTTP-сервис.

## Что не входит в систему

- полноценный пользовательский интерфейс;
- облачный деплой и эксплуатация production-инфраструктуры;
- реальные платежи и обработка чувствительных персональных данных;
- автоматическое исправление инфраструктурных неисправностей;
- полноценная замена существующих ITSM/CMDB-платформ;
- самостоятельное принятие решений языковой моделью в первой версии.

## Инженерная архитектура

Основной поток обработки строится по схеме:

`Request → Job → Dispatcher → Registry → Tool → ToolResult`

- **Request** — запрос на создание или изменение инцидента.
- **Job** — инцидент как единица работы с идентификатором, состоянием, сроками SLA и историей.
- **Dispatcher** — выбирает исполнителя операции, не зная конкретных реализаций инструментов.
- **Registry** — хранит доступные инструменты и предоставляет их по имени операции.
- **Tool** — отдельный исполнитель, например маршрутизация или эскалация.
- **ToolResult** — единый результат выполнения инструмента, включая информацию об ошибке.

Планируемые инструменты: `RoutingTool` для назначения исполнителя и `EscalationTool` для обработки нарушения SLA. Уведомления отправляются через отдельный HTTP-адаптер с timeout и ограниченным retry. Для тестирования сетевого взаимодействия будет использоваться fake-сервис.

## Жизненный цикл инцидента

Основные состояния: `OPEN`, `IN_PROGRESS`, `ESCALATED`, `RESOLVED`, `CLOSED`, `CANCELLED`. Разрешённые переходы и условия их выполнения описаны в [требованиях](docs/requirements.md). Недопустимый переход не должен менять состояние инцидента.

## Перспектива второго семестра

В архитектуре предусмотрен отдельный шов для LLM. Во втором семестре модель можно подключить для классификации текста инцидента, предложения приоритета и подходящего исполнителя. В первой версии маршрутизация и контроль SLA выполняются детерминированной логикой; LLM не является обязательной зависимостью основного процесса.
